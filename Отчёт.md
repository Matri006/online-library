# Отчёт по заданию 1: клиент-серверное приложение «Онлайн-библиотека»

## 1. Доменная область

Приложение автоматизирует работу университетской библиотеки: ведение каталога книг, учёт экземпляров в филиалах и книгохранилищах, регистрацию читателей, выдачу и возврат литературы. Дополнительно оно хранит сведения о том, какие факультеты используют книги, формирует отчёты и журнал изменений.

С приложением работают три категории пользователей: администратор управляет справочниками, учётными записями и всеми операциями; библиотекарь ведёт каталог, фонд и выдачи; сотрудник факультета с ролью VIEWER просматривает данные. Браузер является клиентом, Java-приложение — сервером. Данные передаются по HTTP/1.1 в JSON; сервер проверяет права и корректность операций, PostgreSQL обеспечивает постоянное хранение и целостность.

## 2. Стек реализации

| Компонент | Технология и назначение |
| --- | --- |
| Фронтенд | HTML5, CSS, JavaScript без фреймворков; Fetch API для запросов к серверу |
| Бэкенд | Java 21, Spring Boot 3.5.6, Spring MVC, встроенный Tomcat |
| Доступ к данным | Spring JDBC / JdbcTemplate, HikariCP, PostgreSQL JDBC Driver |
| СУБД | PostgreSQL 16; таблицы, ограничения, индексы, SQL/PLpgSQL-функции и процедуры |
| Миграции | Flyway, последовательные SQL-миграции V1–V4 |
| Безопасность | Spring Security, BCrypt, роли, CSRF-защита, HttpOnly/SameSite cookie |
| Сессии | Spring Session JDBC; общее хранилище в PostgreSQL |
| Сборка и запуск | Maven 3.9.9 в многостадийном Dockerfile, JRE 21 в итоговом образе, Docker Compose |
| Проверки | JUnit 5, Spring Boot Test / MockMvc, Testcontainers с PostgreSQL 16, ArchUnit; Python HTTP smoke-тест |
| Диагностика | SLF4J/Logback в stdout, Actuator `/actuator/health` |

Сохранён существующий Java-стек, чтобы использовать уже реализованные библиотечные правила и тесты. Фронтенд не требует отдельного Node.js-сервера и сборщика, не используются Redis, брокеры сообщений и дополнительные обязательные сервисы. Минимальный стенд содержит два постоянно работающих процесса: веб-приложение и PostgreSQL. Для web-контейнера задан лимит 512 MiB, пул БД по умолчанию ограничен десятью соединениями. Это конфигурация учебного стенда, а не гарантия достаточности памяти при любой нагрузке; для последующих заданий параметры можно менять через окружение.

## 3. Основные сущности

| Сущность / таблицы | Содержимое и связи |
| --- | --- |
| Книга — `book` | Название, издательство, год издания, страницы, иллюстрации, цена |
| Автор — `author`, `book_author` | ФИО автора; связь книги с авторами многие-ко-многим |
| Издательство — `publisher` | Издательство выпускает множество книг |
| Филиал — `branch` | Библиотека или книгохранилище, адрес, телефон, признак активности |
| Место хранения — `storage_location` | Зал или склад внутри филиала |
| Книжный фонд — `book_stock` | Число экземпляров книги в конкретном месте хранения |
| Факультет — `faculty` | Подразделение университета |
| Учебное использование — `book_usage` | Связь книги, филиала и факультета |
| Студент — `student` | Номер студенческого билета, ФИО, факультет, активность |
| Выдача — `loan` | Книга, место, студент, факультет на момент выдачи, даты выдачи/возврата и сотрудники |
| Учётная запись — `app_user`, `app_role` | Логин, BCrypt-хеш пароля, роль ADMIN/LIBRARIAN/VIEWER, активность |
| Аудит — `audit_log` | Автор, время, тип изменения и значения до/после; пароли в аудит не попадают |

`SPRING_SESSION` и `SPRING_SESSION_ATTRIBUTES` — технические таблицы сессий; `flyway_schema_history` — история миграций. Они не являются сущностями предметной области.

Целостность обеспечивается внешними ключами, CHECK-ограничениями и транзакциями. Например, нельзя выдать больше экземпляров, чем доступно, уменьшить фонд ниже числа открытых выдач или оставить книгу без авторов. Исторические записи выдач сохраняются при деактивации читателя или филиала.

## 4. Архитектура и CRUD

Статические файлы находятся в `src/main/resources/static`. Spring Boot отдаёт их по тому же адресу, что и API. Фронтенд и бэкенд остаются логически разными частями клиент-серверного приложения; отдельные контейнеры для них не обязательны.

Путь изменения данных:

1. `app.js` собирает поля формы и отправляет HTTP-запрос с cookie и CSRF-токеном.
2. Spring Security проверяет аутентификацию и права. `AccountRefreshFilter` повторно проверяет актуальность роли и активности пользователя.
3. Контроллер в `controllers` принимает DTO и выполняет валидацию.
4. Сервис в `services` открывает транзакцию и организует бизнес-операцию.
5. Репозиторий в `repository` выполняет параметризованный SQL или вызывает процедуру PostgreSQL.
6. Ограничения и триггеры БД проверяют целостность и записывают аудит. Успешная фиксация операции отражается в консольном логе.
7. Контроллер возвращает JSON/HTTP-статус, интерфейс обновляет каталог либо показывает понятную ошибку.

Полный CRUD реализован для книг:

| Операция | HTTP API | Интерфейс |
| --- | --- | --- |
| Create | `POST /api/books` | «Добавить» в каталоге |
| Read | `GET /api/books` с поиском и пагинацией | Таблица и поиск |
| Update | `PUT /api/books/{id}` | «Изменить» |
| Delete | `DELETE /api/books/{id}`, успех `204` | «Удалить» с подтверждением |

Удаление разрешено только для книги без записей фонда и учебного использования. Иначе возвращается `409 BOOK_IN_USE`. Связи с авторами удаляются вместе с книгой внутри одной транзакции; история аудита сохраняется. Чужие ссылки и история выдач не удаляются каскадно. Для несуществующего идентификатора возвращается `404`, для запрещённой роли или отсутствующего CSRF-токена — `403`.

Для других сущностей реализованы операции, соответствующие их назначению: создание и изменение справочников, студентов и филиалов, изменение фонда, добавление/удаление учебных связей, выдача и возврат книг. Удаление исторических данных не требуется для демонстрации CRUD: четыре операции явно доступны для одной основной сущности — книги.

## 5. Соответствие методологии 12 факторов

Ниже использованы названия факторов с [12factor.net](https://12factor.net/ru/). Часть требований относится к устройству программы, часть — к правилам её разработки и эксплуатации. Для последних описаны и техническая поддержка, и необходимые действия при развёртывании.

### I. Кодовая база (Codebase)

Фронтенд, бэкенд, миграции, тесты и описание окружения образуют одну кодовую базу. Для разработки, тестирования и эксплуатации не нужны отдельные копии исходников с разными настройками. Окружения получают одну выбранную версию кода и различаются конфигурацией.

Кодовая база находится в Git-репозитории `online-library`; фронтенд и бэкенд версионируются вместе. Сдаваемый архив содержит исходники текущего рабочего дерева, без служебной директории `.git` и её локальных настроек. Перед выпуском изменения фиксируются коммитом, а образ получает отдельный тег `APP_VERSION`. История репозитория и разные окружения относятся к одной кодовой базе.

### II. Зависимости (Dependencies)

Java-зависимости объявлены в `pom.xml`, их версии определены Spring Boot parent 3.5.6; версия ArchUnit указана отдельно. Сборочный Docker-образ задаёт Maven 3.9.9 и JDK 21. Итоговый образ содержит JRE и исполняемый JAR со всеми Java-библиотеками. Фронтенд не загружает зависимости из CDN.

Сборка не рассчитывает на Maven, Java или глобальные библиотеки компьютера разработчика. PostgreSQL 16 объявлен в Compose. Python-скрипты используют только стандартную библиотеку; Python и Git нужны для проверочного скрипта/упаковки, но не для работы приложения. Образы ОС и PostgreSQL используют версионные теги, которые могут получать исправления; для повторного развёртывания одного выпуска используется уже собранный образ, а для побитового воспроизведения сборки в дальнейшем следует дополнительно закреплять digest базовых образов.

### III. Конфигурация (Config)

URL и учётные данные PostgreSQL, параметры пула, порт, уровень логов, тайм-аут сессии, Secure cookie и начальные пароли задаются через переменные окружения. Привязки находятся в `application.yml` и `docker-compose.yml`. Менять Java/JavaScript или пересобирать JAR при смене базы и паролей не требуется.

`.env.example` содержит только явно обозначенные учебные значения. Реальный `.env` исключён из Git, Docker build context и архива. Обязательные пароли Compose проверяет до запуска. Привилегированные параметры миграций и первичной инициализации передаются только разовому `release`, а web-процесс получает роль `library_app`.

### IV. Сторонние службы (Backing services)

PostgreSQL — подключаемый внешний ресурс. Java обращается к нему по JDBC URL и учётным данным, а не по локальному пути. Можно переключить приложение на другой сервер PostgreSQL через конфигурацию без изменения кода.

Сервер PostgreSQL имеет собственный жизненный цикл; его данные находятся в отдельном Docker-томе. Замена контейнера приложения не удаляет БД. Для самостоятельного подключения к внешней БД предусмотрен запуск того же JAR/образа с другими переменными. Независимость от конкретного экземпляра PostgreSQL не означает совместимость с другой СУБД: проект намеренно использует возможности PostgreSQL.

### V. Сборка, релиз, выполнение (Build, release, run)

Этапы разделены технически. **Build**: Dockerfile собирает JAR и итоговый образ без подключения к рабочей БД. **Release**: сервис `release` запускает тот же образ с профилем `release` и без HTTP-сервера, применяет Flyway-миграции и идемпотентно создаёт начальные данные. После окончания процесс закрывает Spring context и завершается. **Run**: `app` запускает HTTP-сервер из этого образа с выключенными миграциями.

Compose запускает web только после успешного завершения release. Для выпуска задаётся отдельный `APP_VERSION`; пересборку образа и миграции не выполняют внутри уже работающего web-процесса. Один и тот же образ можно повторно развернуть с соответствующей конфигурацией. Откат приложения и откат схемы БД — разные операции; автоматическое удаление новых данных при откате не предусмотрено.

### VI. Процессы (Processes)

Web-процесс не содержит долговечного пользовательского состояния в своей памяти или файловой системе. Предметные данные, учётные записи, аудит и сессии хранятся в PostgreSQL. Благодаря Spring Session JDBC аутентификация и CSRF-состояние доступны всем экземплярам приложения и сохраняются после перезапуска.

Файлы фронтенда — неизменяемая часть JAR. Локальная память используется для выполнения текущих запросов, пула соединений и служебных объектов. Для работы не требуется локальный каталог пользовательских файлов или закрепление пользователя за определённым экземпляром. Файлы резервных копий создаёт отдельный административный процесс в отдельном томе.

### VII. Привязка портов (Port binding)

JAR запускает встроенный Tomcat и самостоятельно предоставляет HTTP-сервис. Установка приложения во внешний Tomcat/Apache не нужна. Адрес и порт Java-процесса задаются `HOST`/`PORT`; по умолчанию это `0.0.0.0:8080`.

В Compose порт публикуется на `BIND_ADDRESS:APP_PORT`; локальный стенд по умолчанию доступен только на loopback-интерфейсе. Фронтенд получает API через относительные URL, поэтому смена опубликованного порта не требует изменения клиентского кода. HTTP/1.1 подходит для дальнейшего подключения балансировщика.

### VIII. Параллелизм (Concurrency)

Приложение масштабируется запуском дополнительных web-процессов из одного образа. Их сессии и предметные данные общие. Транзакции PostgreSQL и блокировки защищают операции с каталогом и экземплярами от конфликтующих изменений.

`docker-compose.scale.yml` позволяет запустить `--scale app=2` без конфликта фиксированного порта: каждый экземпляр получает отдельный локальный порт. Автоматический HTTP-тест использует одну cookie-сессию на двух экземплярах. Единый внешний адрес и распределение запросов между экземплярами относятся к настройке балансировщика в следующем задании; в текущем стенде проверены сами независимые процессы. Пул соединений ограничен и настраивается под число реплик.

### IX. Одноразовость процессов (Disposability)

Миграции и заполнение демоданными вынесены из запуска web. Это сокращает повторный старт и исключает необходимость миграционных прав у каждого экземпляра. Проверка `/actuator/health` позволяет окружению дождаться доступности приложения и его базы.

Настроен graceful shutdown: при SIGTERM встроенный сервер прекращает принимать новые запросы и ожидает завершения текущих до 20 секунд. Compose даёт контейнеру 30 секунд; Java получает сигнал напрямую благодаря exec-форме ENTRYPOINT. При аварийном завершении незавершённые транзакции откатываются PostgreSQL, зафиксированные данные и сессии остаются в БД. Повторный запуск не требует восстановления локальных файлов web-процесса.

### X. Паритет разработки и эксплуатации (Dev/prod parity)

В локальном окружении и интеграционных тестах используется PostgreSQL 16; замена на H2/SQLite не производится. Применяются те же миграции, JDBC-код, ограничения и процедуры. Docker фиксирует семейство JDK/JRE; один собранный образ предназначен для переноса между окружениями.

Учебные аккаунты и заполнение примерами включаются отдельной настройкой `DEMO_ENABLED`, а не веткой кода для конкретного компьютера. Для публичного размещения меняют значения конфигурации, включают HTTPS/Secure cookie на окружении и используют нужное число экземпляров. Реальный промышленный стенд в рамках задания не развёртывался; совпадение процессов команды, сроков выпуска и настроек инфраструктуры в дальнейшем является организационной обязанностью.

### XI. Журналы (Logs)

Логи Spring Boot, ошибки и сообщения `Committed ...` после фиксации бизнес-операций идут в консоль. Приложение не управляет локальными log-файлами, их архивированием или отправкой во внешнюю систему. Логи доступны через `docker compose logs`; хранение, ротацию и сбор обеспечивает окружение.

`audit_log` выполняет другую задачу: хранит предметную историю изменений как данные приложения. Наличие аудита в PostgreSQL не заменяет поток диагностических логов. Процесс резервного копирования также пишет статус в stdout/stderr.

### XII. Административные задачи (Admin processes)

Миграции и начальная инициализация выполняются разовым процессом `release` из того же образа и той же версии исходников, что web-сервис. Команда `docker compose run --rm --no-deps release` использует штатную конфигурацию подключения и завершается с кодом выполнения; отдельный HTTP-порт не поднимается. Flyway ведёт историю, а инициализация пользователей защищена транзакционной блокировкой и не перезаписывает существующие данные.

Создание роли БД вынесено в `db-init` с клиентом PostgreSQL. Разовый `pg_dump` запускается в окружении базы штатным инструментом PostgreSQL 16; дополнительный процесс резервного копирования включается профилем `ops`. Произвольные административные действия не встроены в обработку пользовательских HTTP-запросов.

## 6. Проверка решения

Полный порядок воспроизведения приведён в [README.md](README.md). Автоматические тесты проверяют бизнес-ограничения, транзакционность, конкурентные выдачи, HTTP-контракты, роли, CSRF, первичную инициализацию и архитектурные границы слоёв. Для удаления добавлены проверки полного HTTP CRUD, сохранения связанных данных и аудита, запрета записи для VIEWER и обработки отсутствующего объекта.

Проверки проведены 2 октября 2026 года на изолированном стенде Docker с реальной PostgreSQL 16:

- сборка Docker-образа;
- 30 автоматических проверок, 0 ошибок, 0 пропусков;
- применение V1–V4 к пустой базе и завершение release;
- запуск двух web-процессов с отдельными портами;
- CRUD через реальный HTTP с одной сессией на двух процессах;
- сохранение аутентификации после перезапуска обоих web-процессов;
- синтаксическая проверка JavaScript командой `node --check`.

Визуальная проверка в управляемом браузере не выполнялась: инструмент браузерной автоматизации был недоступен. Это ограничение проверки; сценарий ручной демонстрации интерфейса описан в README.
